# Gon 스킬팩 설계

작성일: 2026-11-02 · 상태: 검토 대기(승인 전, 제품 코드 없음)

## 1. 의도와 이유

**목표 한 줄**: 전국민 AI 능력 평준화. 스킬, MCP, 프롬프트를 모르는 사람도 자기 AI에 한 줄 아이디어만 말하면, 깊은 질문과 전문가 분업을 거쳐 단일 AI가 그대로 만들 때보다 높은 품질의 결과를 받게 한다.

**왜 지금 이 모양인가**
- 사용자는 서비스 서버에 자기 AI 구독을 붙일 수 없다. 그래서 호스팅 서버가 AI를 대신 호출하는 방식은 기각했다.
- 대신 사용자 본인의 AI와 구독 안에서 도는 **스킬팩**으로 만들고, 진행 상황을 점과 선으로 보여 주는 **읽기 전용 그래프 화면**을 곁들인다.
- 이전 프로젝트 `side_pj`는 너무 비대해지고 토큰을 낭비해서, `gon`을 새로 시작했다. `side_pj`는 반면교사로만 쓰고 기반으로 삼지 않는다.

**대상 사용자**: 이미 CLI형 AI 에이전트(Claude Code, Codex 등)를 설치하고 로그인한 비전문가. 웹·앱 채팅만 쓰는 사람은 이번 범위 밖이다.

## 2. 목표, 비목표, 안티목표

**목표**
- 한 줄 아이디어 → 질문 → 계획 → 승인 → 전문가 병렬 실행 → 결과까지 한 바퀴가 도는 스킬팩
- 진행 과정이 점과 선으로 실시간(단계 단위)으로 보이고, 끝난 뒤 점을 눌러 각자 한 일을 볼 수 있는 화면
- 매 턴 읽히는 내용이 최소인 가벼운 구조(토큰 절약)
- 사용자가 직접 입력하는 두 줄 안팎으로 끝나는 설치

**비목표 (이번 범위 밖)**
- 호스팅 서버, 로그인·DB, 서버가 사용자 AI를 대신 실행하는 기능
- 웹·앱 채팅 전용 사용자 지원(파일 시스템이 없어 기록·그래프 불가)
- 화면에서 요청을 입력하거나 실행을 시작하는 기능
- 전문가 점이 서브에이전트마다 따로 움직이는 정밀 실시간(훅 필요, 후속 선택 기능)
- 3D 오피스 화면, 외부 스킬 저장소 대량 clone

**안티목표 (기술적으로 돌아가도 실패로 보는 것)**
- `side_pj`처럼 파일·레지스트리·스킬 수가 불어나 토큰을 낭비하는 것
- 설치만으로 훅·MCP·서버 등 무엇이든 자동으로 사용자 PC에서 돌게 되는 것
- 사용자가 승인하지 않은 계획으로 실행이 시작되는 것
- 사용자의 전역 설정(전역 CLAUDE.md 등)을 말없이 바꾸는 것
- 검수되지 않은 제3자 스킬이 사용자 동의 없이 설치되는 것

## 3. 제약

- 사용자 AI의 구독과 권한 안에서만 동작한다. 승인 창은 도구 기본 그대로 둔다.
- 플러그인은 설치하면 기본으로 켜지고, 훅·MCP가 있으면 같이 켜진다(Claude Code 공식 문서). 그래서 **훅, MCP, 모니터, 설치 스크립트처럼 자동으로 실행되는 것을 플러그인에 넣지 않는다.** 그래프 뷰어 서버 코드(`viewer/`)는 넣되, 사용자가 요청할 때만 AI가 정확한 명령을 보여 주고 승인받아 실행한다(5.4).
- 스킬 본문은 도구 공통 표준 필드(`name`, `description`)와 상대 경로만 쓴다. Claude 전용 frontmatter와 `${CLAUDE_SKILL_DIR}` 같은 치환 변수는 다른 도구에서 통한다는 근거가 없다.
- 도구 이름(Read, Write, Task 등) 대신 동작("파일 읽기", "하위 작업 병렬 실행")으로 쓰고, 도구별 매핑은 따로 둔다.
- 기록은 프로젝트 안 `.gon/` 폴더에만 쓴다. Codex는 작업영역에서도 `.git`, `.agents`, `.codex`를 읽기 전용으로 두므로 그 아래에는 쓰지 않는다.
- 저장소는 공개(`github.com/2Jaegon/Gon`)다. 비밀값, 개인 경로, 키는 저장소에 넣지 않는다.

## 4. 고려한 접근안과 선택

### 4.1 전체 구조
| 안 | 내용 | 결과 |
|---|---|---|
| C. 호스팅 서버 | 서버가 사용자 AI를 대신 호출 | 기각: 사용자 구독을 붙일 수 없음 |
| A. 웹앱 중심 | 기존 `side_pj`식 백엔드·프론트 서비스 | 기각: 비대, 인증·DB·CLI 서브프로세스 의존 |
| **B+A. 스킬팩 + 선택 UI** | 핵심은 사용자 AI 안의 스킬, 화면은 읽기 전용 | **채택** |

### 4.2 그래프 배치
방사형, 단계 흐름형, 쌓이는 형 중 **단계 흐름형 + 쌓이는 형 혼합**을 채택했다. 요청 하나가 메인 점에서 가지 하나로 뻗어 왼쪽에서 오른쪽으로 흐르고(질문 → … → 결과, 전문가는 병렬로 갈라짐), 끝난 가지는 흐려져 위·아래로 쌓인다. 점을 누르면 오른쪽 패널에 그 점이 한 일이 뜬다. 목업은 `.superpowers/brainstorm/*/content/graph-hybrid.html`에 있다(참고용, 색상은 보라 위주라 구현 때 재검토).

### 4.3 단계 담당
| 안 | 내용 | 결과 |
|---|---|---|
| 자체 역할 카드만 | 전부 Gon이 직접 작성 | 기각: 방법론을 직접 만들고 유지해야 함 |
| A. 순수 지휘자 | 단계마다 기존 스킬 이름만 호출 | 기각: 스킬이 없거나 이름이 다르면 그 단계에서 멈춤 |
| **B. 지휘자 + 작은 대체 지침** | 기존 스킬을 쓰되, 없을 때만 읽는 내장 카드(단계당 10~20줄)를 둠 | **채택** |
| `find-skills`를 기본 처리로 | 스킬이 없으면 항상 `find-skills`로 찾아 설치 | 기본으로는 기각, **선택 업그레이드로 채택**(5.1.1) |

이유: Antigravity·Gemini는 "최선 노력" 지원인데, 그 도구들에서는 외부 스킬이 안 깔릴 가능성이 높다. 대체 카드는 필요할 때만 읽어서 매 턴 토큰을 늘리지 않는다. `find-skills`는 먼저 설치돼 있어야 하고, 네트워크와 외부 레지스트리에 의존하며, 검수되지 않은 제3자 스킬을 들여오고, 설치 직후 재시작이 필요할 수 있어 "항상 되는 바닥"이 될 수 없다. 사용자가 제안했고, 바닥이 아니라 그 위의 선택 단계로 받아들였다.

### 4.4 설치 방식
사용자가 직접 입력하는 두 줄(터미널의 `claude plugin ...` 명령, 이후 재시작 또는 `/reload-plugins`)을 기본으로 한다. `/plugin` 슬래시 명령은 이 환경(확장 프로그램)에서 동작하지 않음을 2026-11-02에 확인했다. "GON 설치해줘" 한 줄은 AI가 외부 문서의 명령을 실행하는 구조라 문서 변조·사칭에 취약하므로, 고정된 명령만 담은 `INSTALL.md`를 AI가 읽고 **실행 전에 보여 준 뒤 승인을 받는** 보조 수단으로 둔다.

## 5. 결정된 설계

### 5.1 흐름과 깊이
기본 흐름은 7단계이며 각 단계가 그래프의 점 하나가 된다. 계획 승인은 모든 깊이에서 필수다.

| # | 단계 | 하는 일 | 담당 후보(우선) | 대체 카드 | 점 |
|---|---|---|---|---|---|
| 1 | 질문 | 사용자의 한 줄 요청 접수 | — | — | 메인에서 시작 |
| 2 | 그릴링 | 모호한 부분을 추천 답과 함께 질문, 결과를 `brief.md`로 확정 | `grilling` (mattpocock-skills) | `grill` 카드 | interview |
| 3 | 기획 | 목표·범위·접근안 정리 | `superpowers:brainstorming`, ECC 기획 스킬/에이전트 | `plan` 카드 | plan |
| 4 | 점검 | 그릴링으로 기획이 맞는지 확인, **사용자 승인 1회(게이트)** | `grilling`, ECC `council`(선택) | `check` 카드 | check |
| 5 | 작업 구성 | 어떤 전문가를 몇 명, 어떤 순서로 부를지 정함 | `superpowers:writing-plans`, ECC `plan-orchestrate`/`team-builder`(선택) | `compose` 카드 | compose |
| 6 | 실행 | 전문가 서브에이전트 병렬 실행, 각자 결과를 파일로 | `superpowers:subagent-driven-development` 등 | 범용 `gon-expert` | 전문가 점 여러 개 |
| 7 | 결과 | 결과 종합과 검증 | `superpowers:verification-before-completion` | `lead` 카드 | lead |

**깊이 3단계** (사용자가 한 마디로 바꿀 수 있고, 말하지 않으면 보통)
- **빠름**: 그릴링 최대 1라운드 → 한 줄 계획 승인 → 서브에이전트 없이 단일 실행 → 결과
- **보통(기본)**: 7단계 전체, 전문가 2~4명, 점검 포함
- **깊게**: 보통 + QA·보안 점검 + 수정 1회. ECC 스킬은 이 단계에서만 선택적으로 사용

그릴링은 최대 2라운드, 라운드당 질문 4개 이하, 질문마다 추천 답을 붙인다(제안값, 구현 때 조정 가능).

#### 5.1.1 단계 담당 스킬이 없을 때 (순서)
1. 담당 스킬이 설치돼 있으면 그것을 쓴다.
2. 없으면 **멈추지 않고 내장 대체 카드로 진행한다.** 오프라인에서도, 어떤 도구에서도 돌아가는 바닥이다. 결과 화면과 기록에 `fallback`이라고 표시한다.
3. 사용자가 원하거나 더 나은 스킬이 필요해 보이면 `find-skills`로 후보를 찾아 보여 준다. **설치는 출처, 하는 일, 설치 위치를 미리 보여 주고 사용자가 동의한 뒤에만** 한다. 설치 후 재시작이 필요하면 그 사실을 알리고, 이번 한 바퀴는 대체 카드로 마친다.
4. `find-skills` 자체는 필수 의존이 아니라 선택 의존이다. 없으면 온보딩이 설치 명령을 안내만 하고 자동 설치하지 않는다. 설치 방식(외부 레지스트리 조회 등)과 도구별 동작은 아직 확인 전이다.
5. 이렇게 들여온 제3자 스킬은 검수되지 않은 외부 자료로 취급한다(5.8).

#### 5.1.2 실행의 결과물: 실제 코드
- 6단계의 결과물은 **사용자 프로젝트 폴더 안의 실제 코드와 파일**이다. 설계 요약, 근거, 점별 산출물은 `.gon/`에 남긴다.
- 작업 구성 단계(5)에서 전문가마다 **맡을 파일·폴더를 겹치지 않게 나눠** 병렬 쓰기 충돌을 막는다. 공유 파일(설정, 라우터 등)은 한 전문가만 맡거나 총괄이 합친다.
- 새 파일 생성은 계획 승인에 포함된다. **기존 파일을 덮어쓰거나 삭제하는 것**은 계획에 파일 목록을 보여 주고 승인에 포함시키며, 목록에 없는 기존 파일은 건드리지 않는다.
- 코드는 프로젝트 폴더 안에만 쓴다. 폴더 밖, 전역 설정, 비밀값 파일(`.env` 등)은 건드리지 않는다.
- 기록 줄에 바꾼 파일 목록 `files`를 남기고, 점 패널에서 볼 수 있게 한다. "빠름"은 작은 변경만 하는 단일 실행이다.
- 코드를 쓰는 만큼 승인 창이 늘어난다. 온보딩에서 이 점을 미리 안내한다(도구의 승인 모드를 우회하도록 안내하지 않는다).

### 5.2 저장소 구조 (제안, 빌더가 조정 가능)
```
gon/ (공개 저장소 2Jaegon/Gon)
  .claude-plugin/marketplace.json       Claude Code 마켓플레이스 목록
  .codex-plugin/ , .antigravity-plugin/ , gemini-extension.json   도구별 얇은 매니페스트
  plugins/gon/
    skills/gon/SKILL.md                 진입 스킬: 설명 한 줄 + 흐름·게이트·깊이·기록 규칙·온보딩
    skills/gon/stages.md                단계표(담당 스킬 이름, 도구별 호출 표기)
    skills/gon/cards/*.md               대체 지침 카드(없을 때만 읽음)
    skills/gon/tools/{claude,codex,antigravity,gemini}.md   도구별 동작 매핑과 병렬 지시문
    agents/ (도구별 형식)               범용 gon-expert 하나
    viewer/                             그래프 화면과 로컬 서버
  INSTALL.md                            고정 명령만 담은 설치 안내
  README.md                             사람용 설치 두 줄
  docs/superpowers/specs/               이 문서
```
원칙: 원본은 `skills/gon/` 하나이고, 도구별 파일은 얇게 둔다. 서브에이전트 정의 형식이 도구마다 다르므로(`.claude/agents/*.md`, `.codex/agents/*.toml`, `.gemini/agents/*.md`, `.agents/agents/*.md`) 범용 `gon-expert` 하나만 도구별로 만든다.

### 5.3 기록 규격 (`.gon/<run_id>/`)
요청 하나당 폴더 하나, 안에 `events.jsonl`과 각 점의 산출물 `*.md`를 둔다.

- `events.jsonl`은 한 줄이 이벤트 하나이고, 같은 `id`의 줄을 차례로 합쳐 뒤에 온 값을 그 점의 최종 상태로 쓴다. 깨진 줄은 화면이 건너뛴다.
- **기록은 지휘자(메인 AI)만 쓴다.** 병렬 서브에이전트는 자기 산출물 `.md`만 쓰고 기록 줄은 쓰지 않는다. 동시 쓰기 충돌을 피하고 쓰기 횟수를 줄이기 위해서다(요청당 약 8회, 단계마다 여러 줄을 한 번에 이어 붙임).
- 실시간 정밀도는 단계 단위다. 전문가 점 4개가 함께 켜졌다 함께 꺼진다.
- 메인 점은 파일이 없는 가상 루트다. 각 요청의 첫 노드가 `from:["main"]`을 가진다. `run.end` 이후 그 가지를 흐리게 표시하고, 쌓는 순서는 폴더 이름(시각) 순이다.
- 재시도는 새 id(`fe-2`)로 남긴다. `running`이 10분 넘게 그대로면 화면이 "멈춤?"으로 표시한다.
- 이어 쓰기는 OS별 셸(bash `cat >> f <<'EOF'`, PowerShell `Add-Content` + 문자 그대로 here-string)로 한다. 별도 스크립트는 두지 않는다.


### 5.4 그래프 화면과 서버
- **프론트엔드**: 읽기 전용 그래프(5.1의 점·선, 4.2의 모양). 마크다운은 정제해서 렌더하고 CSP를 적용한다.
- **백엔드**: `127.0.0.1`에서만 열리는 작은 로컬 서버(Node 단일 파일). `.gon/`을 읽어 화면에 실시간으로 전달하는 것만 한다. 실행 시마다 바뀌는 토큰으로 접근을 막고, 경로 탈출을 차단하며, AI 실행·설치 엔드포인트는 두지 않는다.
- **Node가 없는 PC**: 브라우저가 `.gon` 폴더를 직접 열어 1초마다 다시 읽는 방식(File System Access API)으로 대체한다. Chrome·Edge에서만 되고 `file://`에서 되는지는 아직 확인 전이다.
- 요청 입력과 실행은 항상 사용자의 AI 채팅에서 한다.
- 화면은 AI가 "그래프 보여줘"라는 말에 서버를 띄우고 브라우저를 열어 준다(구현 방법은 빌더 판단, 실행 전 사용자에게 보여 주고 확인).

### 5.6 설치와 첫 실행
1. 사용자가 README의 두 줄(`claude plugin ...`)을 터미널에 입력하고 `/reload-plugins`(또는 재시작)를 한다. AI가 Bash로 이 두 줄을 대신 실행하는 것은 실행 전에 보여 주고 승인받는 조건으로만 한다. `/reload-plugins`를 AI가 호출할 수 있다는 문서는 없다.
2. 보조 수단으로 "GON 설치해줘"가 있다. AI는 고정 명령만 담은 `INSTALL.md`(버전 태그로 고정한 주소)를 읽고, 자기가 어떤 도구인지 판별한 뒤 공식 설치 명령을 **실행 전에 보여 주고 승인을 받는다.**
3. 설치 후 첫 `/gon`이 온보딩을 맡는다: 권장 스킬(grilling, superpowers)이 있는지 확인하고 없으면 설치 명령을 보여 준다(자동 설치 안 함, 거절해도 대체 카드로 진행) → 선택 스킬(`find-skills`, ECC)을 안내만 한다 → `.gon/` 폴더 생성 동의 → 그래프 화면 사용 여부 → 시험 요청 1건.
4. 삭제는 도구의 공식 제거 명령으로 한다. 전역 설정은 건드리지 않으므로 되돌릴 것이 없다.
5. `INSTALL.md`에는 다른 파일을 내려받거나 실행하라는 지시를 넣지 않는다.

### 5.7 토큰 절약 원칙
1. 매 턴 읽히는 것은 스킬 설명 한 줄과 범용 서브에이전트 설명 하나뿐이다(역할마다 에이전트를 만들지 않는다).
2. `/gon`을 부를 때 `SKILL.md`만 읽는다. 단계표·카드·도구별 매핑은 그 단계에 들어갈 때만 읽는다.
3. 지휘자는 전문가에게 카드·산출물 **경로만** 넘기고, 전문가가 직접 읽는다.
4. 전문가의 출력은 600자 이하로 제한하고, 지휘자에게는 한 줄 요약과 경로만 돌려준다.
5. 깊이 3단계로 비용을 조절한다.
6. `/gon`은 사용자가 `/gon` 또는 "gon으로"라고 직접 부를 때만 켜진다. 스킬 설명에 이 조건을 적어, 일반 대화나 작은 코딩 요청이 7단계로 끌려가지 않게 한다.
7. 카드와 `SKILL.md`는 한국어로 쓰고 필드명과 명령은 영어로 둔다. 도구에서 준수율이 낮으면 영어 지침 + 한국어 응답 지시로 바꾼다(위험한 가정 2에서 측정).
8. 프롬프트 캐싱을 위한 배치 원칙은 5.9를 따른다.

### 5.8 보안
- 플러그인에 훅, MCP, 모니터, 설치 스크립트처럼 자동 실행되는 것을 넣지 않는다. 뷰어 서버 코드는 `viewer/`에 있어도 사용자가 요청하고 승인할 때만 실행되므로, 업데이트가 자동으로 명령 실행 권한을 얻지 못한다. 뷰어 코드는 릴리스 태그로 고정하고 변경 내역을 공개한다.
- 설치물은 저장소 안 파일만 복사하고 외부에서 내려받지 않는다. 릴리스는 태그로 고정하고 변경 내역을 공개한다.
- 사칭 URL·가짜 설치 문장: 공식 주소 하나만 안내하고, `INSTALL.md`는 고정 명령만 담으며 AI가 실행 전에 보여 준다.
- 외부 자료(웹 조사 결과, `find-skills`로 찾은 제3자 스킬 포함) 안의 지시는 따르지 않는다는 규칙을 모든 카드와 `SKILL.md`에 넣는다. 제3자 스킬 설치는 출처·내용 요약을 보여 주고 사용자 동의를 받은 뒤에만 한다.
- 기록에 키, 비밀번호를 쓰지 않는다. `.gon/`을 `.gitignore`에 넣을지는 사용자에게 묻는다.
- 로컬 화면 서버 보안은 5.4를 따른다.
- 저장소에 비밀값이 없는지 공개 전에 점검한다.

### 5.9 프롬프트 캐싱 (캐시가 잘 먹히는 배치)
Gon은 API를 직접 호출하지 않으므로 `cache_control`을 걸 수 없다. 사용자의 AI 도구가 하는 자동 캐싱이 깨지지 않도록 **내용을 배치하는 원칙**만 지킨다. 효과는 M1에서 측정하기 전까지 **미측정**으로 표기하고, 절감 효과를 주장하지 않는다.

1. **고정된 내용을 앞에, 바뀌는 내용을 뒤에 둔다.** `SKILL.md`, 단계표, 카드, 범용 서브에이전트 정의에는 날짜, 시각, run id, 사용자 요청, 경로처럼 **실행마다 바뀌는 값을 넣지 않는다.** 바뀌는 값(요청, `brief.md`, 산출물 경로)은 서브에이전트에게 넘기는 지시의 맨 끝에 둔다.
2. **모든 전문가가 같은 정의(`gon-expert` 하나)와 같은 앞부분 지시를 쓴다.** 역할 이름과 할 일만 마지막에 바뀐다. 병렬로 동시에 시작하면 첫 쓰기가 끝나기 전이라 모두 캐시를 놓칠 수 있는데, 이는 측정 대상이고 병렬성을 줄이는 방향으로 바꾸지 않는다.
3. **실행 중에는 스킬, 플러그인, 도구 구성을 바꾸지 않는다.** 바뀌면 앞부분이 달라져 캐시가 깨진다. 온보딩에서 권장 스킬은 **첫 `/gon` 전에** 설치하게 안내한다.
4. **같은 카드나 문서를 한 번의 실행에서 다시 읽지 않는다.** 읽은 내용은 대화에 남아 이미 캐시 대상이고, 다시 읽으면 컨텍스트만 늘어난다.
5. **대화 앞부분을 고쳐 쓰지 않는다.** 기록(`events.jsonl`)은 이어 쓰기만 하고, 이미 보여 준 내용을 다시 요약해 앞에 끼우지 않는다.
6. **긴 공백 뒤에는 캐시가 만료될 수 있다**(유지 시간은 도구와 요금제에 따라 다름). 계획 승인 대기가 대표적이므로 승인 질문을 짧게 하고, 이 비용은 측정에 포함한다.
7. **캐시를 맞추려고 지침을 부풀리지 않는다.** 앞부분이 캐시 최소 길이에 못 미쳐도 늘리지 않는다(토큰 절약 원칙이 우선).
8. **측정**: Claude Code 세션 기록의 `usage`(`input_tokens`, `cache_creation_input_tokens`, `cache_read_input_tokens`, `output_tokens`)를 합산하는 개발용 도구 `tools/measure-usage.mjs`를 M1에서 만든다. 캐시 읽기 비율 = 캐시 읽기 ÷ (일반 입력 + 캐시 쓰기 + 캐시 읽기). 참고값: 이 설계 세션의 기록은 약 98%였지만, 긴 대화 한 세션의 값일 뿐 Gon의 값이 아니다.

## 7. 성공 기준과 위험한 가정

**성공 기준**: 비전문가가 설치 두 줄(+재시작) 안에 첫 결과까지 가고, 같은 아이디어를 단일 대화로 만든 것보다 결과가 낫다고 평가하며, 요청당 토큰이 허용 범위 안이다.

**위험한 가정과 먼저 할 검증**
1. 대상 사용자가 CLI 에이전트를 이미 설치·로그인했고 두 줄로 설치를 마친다 → M4 관찰 테스트(웹 읽기 도구가 켜져 있는지도 함께 확인)
2. 작게 나눈 지침만으로 모델이 흐름·게이트·기록 규격을 도구마다 안정적으로 지킨다 → 아이디어 10개 × 도구별로 단계 누락률, JSONL 줄 파싱 성공률, 요청당 토큰을 채점. 먼저 M1 직후에 Claude Code로 시험
3. 전문가 팀 방식이 단일 대화보다 확실히 낫고 그 비용을 감수할 만하다 → 블라인드 A/B, 깊이별 소요량 측정
4. 지휘자가 단계마다 부르는 스킬 이름과 호출 표기가 도구마다 다를 수 있다 → 도구별 실측 후 `stages.md`에 반영
5. AI의 Bash 도구가 `claude`·`codex` 등 명령을 PATH에서 찾는지(특히 Windows), 플러그인 캐시 폴더 읽기에 권한 창이 뜨는지 → M1 초반에 실제 설치 시험
6. `find-skills`가 각 도구에서 동작하고 설치 전 출처 확인과 동의 흐름을 만들 수 있다 → M1 이후 선택 기능으로 도구별 시험(실패해도 대체 카드가 바닥을 보장)
7. 5.9의 배치 원칙이 실제로 캐시 읽기 비율을 올린다 → 원칙을 지킨 버전과 어긴 버전을 같은 요청으로 비교 측정(측정 전에는 효과를 주장하지 않는다)

## 8. 확인된 사실과 미확인

**확인됨(공식 문서)**: Claude Code는 `claude plugin marketplace add`, `claude plugin install`, `update`, `uninstall`이 있고 일반 플러그인은 프롬프트 없이 설치된다. 플러그인 하나에 skills, agents, commands를 함께 넣을 수 있고 `plugin.json`의 필수 필드는 `name` 하나, `marketplace.json`은 `name`, `owner`, `plugins`가 필수다. 설치 후 같은 세션에서 쓰려면 사용자가 `/reload-plugins`를 입력하거나 재시작해야 한다. 서브에이전트는 기본 동시 20개까지, 권한은 메인 세션 모드를 따른다.
**확인됨(조사)**: Codex·Antigravity·Gemini CLI 모두 `SKILL.md` 표준과 `.agents/skills` 경로를 읽고, 각자 플러그인/확장 배포 수단이 있다. superpowers가 한 저장소에 도구별 설치 파일을 함께 둔 선례가 있다.
**미확인**: 5.5 표의 설치 명령은 문서와 README에서 읽은 것이고 실제 설치 시험 전이다. Claude 전용 frontmatter를 다른 도구가 무시하는지, `file://`에서 폴더 읽기가 되는지, Gemini 병렬 실행, 도구별 스킬 호출 표기, `find-skills`의 설치 방식과 도구별 동작은 실측이 필요하다.

## 10. 저장소와 배포 메모

- `gon` 폴더를 새 git 저장소로 시작한다(`git init`, `.superpowers/`는 `.gitignore`에 추가).
- 원격은 `https://github.com/2Jaegon/Gon.git`(공개)이다. 사용자가 이 저장소에 현재 프로젝트를 **덮어쓰고 기존 파일을 모두 삭제해도 된다**고 말했다. 2026-11-02 확인 결과 원격에는 `main` 브랜치 하나(커밋 `48c034b`)가 있고, 그 커밋은 `side_pj` 로컬 저장소에도 있다.
- 덮어쓰기(강제 푸시)는 되돌릴 수 없고 공개되므로, **푸시 직전에 지워지는 것과 올라가는 것을 보여 주고 한 번 더 확인받는다.** 브랜치 보호 설정은 확인하지 못했다.
- `side_pj`의 `gon` 원격이 같은 주소를 가리키므로, 덮어쓴 뒤 그쪽 로컬 추적 정보는 맞지 않게 된다.

## 11. 반면교사 (side_pj에서 피할 것)

## 12. 이 문서에서 제가 정한 것 (사용자 확인 필요)

- 깊이별 단계 구성(특히 "빠름"은 승인 게이트를 유지하는 단일 실행으로 정의)
- 그릴링 최대 2라운드, 라운드당 질문 4개 이하
- 전문가 출력 600자 제한과 "경로만 전달" 규칙
- 기록은 지휘자만 쓰고, 이벤트 형식과 상태값의 이름
- 마일스톤 순서(M1~M4)와 완료 기준
- 범용 서브에이전트 하나만 두는 구조
- 대체 지침 카드 후보 5장(grill, plan, check, compose, lead)
- `find-skills`는 대체 카드 위의 선택 단계이며, 제3자 스킬은 동의 후에만 설치
- 뷰어 서버 코드는 플러그인 `viewer/`에 두고 사용자 요청과 승인 때만 실행("마크다운만" 규칙을 "자동 실행 없음"으로 완화)
- `/gon`은 사용자가 직접 부를 때만 켜짐
- grilling·superpowers는 필수가 아니라 권장(없어도 대체 카드로 진행)
- 토큰 예산 숫자는 M1 측정 뒤 확정, 10개 아이디어 채점 하네스는 M4
- 카드와 `SKILL.md`는 한국어, 필드명과 명령은 영어
- 코드 충돌 방지(전문가별 파일 소유)와 기존 파일 덮어쓰기 승인 방식(5.1.2)
- 참고: 이 PC에는 `claude`, `codex`, `agy`(1.4.11), `gemini`, Node 24가 설치돼 있어 M2·M3 시험이 가능하다(로그인 상태는 시험 때 확인)
- 프롬프트 캐싱은 직접 설정할 수 없으므로 배치 원칙(5.9)으로 적용하고, 효과는 M1 측정 전까지 미측정으로 표기
- 설치 안내를 `claude plugin ...`(터미널) 형태로 바꿈(확장 프로그램에서 `/plugin`이 안 됨). AI가 Bash로 대신 실행하는 것은 보여 주고 승인받는 조건
